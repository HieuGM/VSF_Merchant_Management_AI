# Memory Architecture Recommendation — Vietnamese Restaurant Assistant (CrewAI 1.15.5 + Postgres 18)

> Synthesis of 5 research angles (taxonomy, CrewAI-native, frameworks, prod-pattern, Postgres-native) against the grounded current-architecture map. All file:line refs verified against source.
>
> Generated by `memory-system-research` workflow (6 agents, ~316k tokens). Research-only output — not yet approved for implementation.

---

## 1. Executive Summary (BLUF)

The user conflates two distinct problems.

- **P1** (recall ~20 messages within ONE conversation) is a **windowing / token-budget** problem. The rows already exist in `chat_messages` keyed by `session_id`, contiguous and ordered — today capped at `get_recent_turns(limit=4)` and anaphor-gated by `_references_prior`.
- **P2** (recall across ~20 PAST conversations for a returning user) is a **storage + distillation + retrieval** problem. It is today **UNREPRESENTABLE**: `chat_sessions.user_id` is hardcoded `None` on auto-create [chat_message_repository.py:109], so conversations are not queryable per-user.

**DEFAULT PATH** (YAGNI-ordered, Postgres-native, zero new infra first):

- **P1**: widen `get_recent_turns` limit 4→~16; add a ~2000-char budget in `_format_prior_context` that trims OLDEST pairs first; tier `_references_prior` (always inject last 2-4 turns; inject 5-16 only when anaphoric). Defer a rolling summarizer until telemetry shows real >30-turn conversations.
- **P2**: (1) fix `user_id` binding in `_ensure_session` + FE sends `user_id` + add `list_recent_summaries(user_id, limit=20)` query; (2) write a one-line per-conversation DISTILLATE at close into the ALREADY-EXISTING DEAD `chat_sessions.context_snapshot_json` column; (3) recall last ~20 distillates via folded-Vietnamese keyword/ILIKE (reuse `active_constraints_loader.fold_diacritics`); (4) derive cuisine-affinity + price-band aggregates from the existing `user_liked_merchants` table.

**VERDICTS**: KEEP CrewAI `memory=False`. AVOID all frameworks now (mem0 is the only aligned one but gated on embedder+pgvector+proven need; Letta/Zep/LangMem/LlamaIndex all wrong-fit or anti-YAGNI). DEFER embeddings/pgvector until `probe_fpt_embedding.py` passes AND >50 convs. Re-run GT eval (baseline `routing_accuracy=0.82`) after each phase; rollback if not ≥ baseline. Cross-conv injection specifically risks shifting clarification behavior.

**DB-VERIFIED FACTS** (postgres-native researcher, live DB Postgres 18.4 / `postgres:18-alpine`):
- pgvector is **NOT** available in the current image (needs image swap → `pgvector/pgvector:pg18`).
- `pg_trgm` + `unaccent` **ARE** available (contrib ships; `CREATE EXTENSION` only, no image swap).
- No Vietnamese FTS config exists (would be hand-built + poor raw-VN tokenization) → prefer `pg_trgm`+`unaccent` over FTS.

## 2. Core Insight — P1 vs P2 Are Different Problems

| | P1 (~20 messages, ONE conv) | P2 (~20 PAST conversations) |
|---|---|---|
| **Nature** | Prompt-fit / token-budget | Storage + distillation + retrieval |
| **Data today** | Exists in `chat_messages`, contiguous, ordered by `session_id` | NOT queryable per-user (`user_id=None` on auto-create) |
| **Mechanism** | Fixed sliding window + char/token budget + tiered anaphor gate | Per-user session-keying + per-conv distillate store + keyword (later embedding) recall |
| **Reachable by window tuning?** | YES (necessary, + budget) | NO — different `session_id`s are unreachable from any one window |

**Conflation failure modes to avoid**: (a) trying to solve P2 by widening the P1 window — bounded by `session_id` by construction; (b) solving P1 with CrewAI semantic memory — P1 is chronological/ordered, not semantic.

## 3. Recommendation for ~20 MESSAGES (P1)

Stay on the fixed sliding window — just retune. Three concrete edits, **zero new infra**:

### 3.1 Widen the window
- Bump `get_recent_turns` default `limit` 4→~16 at **chat_message_repository.py:69**.
- Pass an explicit limit at the only call site **customer_flow.py:1153** (today uses the default).
- Index `ix_chat_messages_session_timestamp(session_id, timestamp)` already supports a larger limit — **no migration**.
- Raise `active_constraints_loader._SESSION_WINDOW=8` [**active_constraints_loader.py:46**] to track (e.g. →16) so constraint extraction sees the same widened horizon.

### 3.2 Add a token/char budget in `_format_prior_context` [customer_flow.py:1272-1329]
Today the Vietnamese "DỮ LIỆU LỊCH SỬ" block emits all prior pairs **unbounded** (each pair = user text + top-3 merchants + `exclude_ids`, ~80-150 chars). Add a **~2000-char ceiling**: keep NEWEST pairs verbatim, drop OLDEST pairs (and their merchant lists) first when over budget. This is the only real P1 risk at N=20 — without it every prompt bloats ~3-6k tokens.

### 3.3 Tier the `_references_prior` anaphor gate [customer_flow.py:1433-1443]
Today it is **binary**: `prior_context` injected only if the query has an anaphor / refinement-marker / name-match; else `""` (fresh-search isolation) or `_NO_PRIOR_NOTE` (anti-confabulation). At N=20 this is a liability — fresh searches lose ALL recall, but always-on injection bloats non-anaphoric turns. Make it **tiered**:
- ALWAYS inject the last **2-4 turns** (cheap; keeps recent anaphora alive on fresh-search turns too);
- Inject turns **5-16 ONLY** when the anaphor/refinement/name-match fires;
- Keep `_NO_PRIOR_NOTE` for the genuinely-fresh case.

### 3.4 Defer the rolling summarizer (YAGNI)
A rolling summary (LangChain `ConversationSummaryMemory` / MemGPT core-memory rewrite equivalent) is **speculative** at N=20 — restaurant conversations are short (a few search turns), and verbatim-with-budget is usually tolerable. Defer until **close-telemetry shows real conversations exceeding ~30 turns**. If later justified: `_format_prior_context` emits a "TÓM TẮT" prefix (rolling summary of msgs 1..N-4) + verbatim last 4; reuse FPT `gpt-oss-20b` for the call. **No DB change, no embedder.**

## 4. Recommendation for ~20 CONVERSATIONS (P2)

Postgres-native, **no embedder, no pgvector, no new service**. Four steps:

### 4.1 Fix the cross-conv key (PREREQUISITE — blocks everything)
- Stop hardcoding `user_id=None` in `_ensure_session` [**chat_message_repository.py:103-110**]; accept and persist the client-supplied `user_id` on `chat_sessions`.
- Add `list_recent_summaries(user_id, limit=20)` query (ORDER BY `closed_at`/`updated_at` DESC).
- This is **partly a FE change** (FE must send `user_id` on session create) — see Open Questions §10.

### 4.2 Per-conversation DISTILLATE — what it should BE for a restaurant recommender (KISS, structured not free-text)
One-line Vietnamese **intent+outcome** summary written by ONE LLM call (`gpt-oss-20b`) at conversation close / idle timeout / like-event, **OFF the hot path**. Example:
> "Tìm phở Cầu Giấy, so sánh 3 quán, đã thích Phở Lâm (dị ứng tôm)"

**STORE** in the ALREADY-EXISTING but DEAD `chat_sessions.context_snapshot_json` column (verified present, unused in the memory path) — **zero schema migration, no new table**. Do NOT build a free-text memory graph.

### 4.3 Complementary structured slots (mostly already populated — just query them)
| Slot | Source today | Action |
|---|---|---|
| Allergies/diet notes | `user_profiles.context_memory` JSONB (FIFO-8, folded-Vietnamese triggers) [context_memory_service.py:35-53] | KEEP; optionally broaden triggers to durable price/distance ("luôn dưới 100k", "chỉ ăn gần nhà") |
| Cuisine affinity + price-band | `user_liked_merchants` table (write-only-positive, no decay) | DERIVE as aggregates (count by cuisine, avg liked-merchant price) — no new writes, just a query; powers "gợi ý giống quán từng thích" alongside the existing `liked_merchant_ids` ranking boost |
| Per-conv summary | (none) | ADD — slot 4.2 above |

These three slots cover **~90% of real cross-conv recall need deterministically**.

### 4.4 Retrieval without embedder
- `SELECT` last ~20 distillates `WHERE user_id=:u ORDER BY closed_at DESC`, then **folded-Vietnamese ILIKE/keyword filter** on the current query's cuisine + area tokens (reuse `active_constraints_loader.fold_diacritics`).
- Surface top-K within the same char budget as P1.
- Inject as a **"LỊCH SỬ TRƯỚC ĐÓ"** block.

**DEFER embeddings/pgvector** until (a) `probe_fpt_embedding.py` confirms a Vietnamese-competent embedder, AND (b) conversation count grows past ~50-100. At N=20, linear scan of summaries beats a vector index on KISS grounds. Optional Phase-2b: add `pg_trgm`+`unaccent` (extensions already available, no image swap) for diacritics-folded fuzzy keyword recall if plain ILIKE proves too narrow.

## 5. YAGNI-Ordered PHASES

### Phase 1 — CHEAPEST, ZERO NEW INFRA, HIGHEST VALUE (ship first)
**What:** P1 widen+budget+gate (§3) + P2 user_id binding + list-sessions query + repurpose `context_snapshot_json` distillate + summary-on-close + folded-ILIKE recall + derived aggregates (§4). Plus **instrument**: log real P95 conversation length (turns) + token-budget hit-rate.
**Files touched:** `chat_message_repository.py`, `customer_flow.py`, `active_constraints_loader.py`, `context_memory_service.py` (optional trigger broadening), a new small summarizer module (<200 LOC, kebab-case), FE session-create client.
**Infra:** NONE. No DB migration (dead columns already nullable JSONB; index already exists), no embedder, no pgvector, no image swap, no new service.
**GT impact:** P1 window+budget = routing-NEUTRAL. P2 distillate injection = COULD shift clarification → must re-eval. Re-run GT eval (baseline 0.82); rollback if not ≥ baseline.
**Effort:** ~1-2 days. Closes ~90% of the stated need.

### Phase 2 — KEYWORD FUZZY RECALL (only if Phase-1 plain ILIKE proves too narrow)
**What:** `CREATE EXTENSION pg_trgm` + `unaccent` (both already AVAILABLE, verified); functional GIST index on `unaccent(distillate_text)`; `similarity()`/`%` recall as a second leg over distillates. Diacritics-fold solves the no-tone Vietnamese query case ("pho bo" → "phở bò") out of the box; typo-tolerant; deterministic; no embedder.
**Files touched:** a migration (2x CREATE EXTENSION + 1 functional index), recall query in the distillate-retrieval module.
**Infra:** 2x CREATE EXTENSION (no image swap, no rebuild). No embedder.
**GT impact:** Recall-quality change only; re-eval (clarification could shift); rollback if not ≥ baseline.
**Effort:** ~0.5 day. **Prefer this over custom Vietnamese FTS** (which needs a hand-built config + container-layer stopwords file and tokenizes raw Vietnamese poorly).

### Phase 3 — EMBEDDINGS / pgvector (ONLY if Phase-2 keyword recall is DEMONSTRABLY insufficient)
**What:** Swap docker image `postgres:18-alpine` → `pgvector/pgvector:pg18` (data volume survives, container recreated); `CREATE EXTENSION vector`; add `halfvec` column on distillates + HNSW index + cosine top-k query path. **GATED** on first running `probe_fpt_embedding.py` and confirming a Vietnamese-competent embedder (candidates: FPT bge-m3 / Qwen3-Embedding-8B / FPT-VN-Embedding; fallback local `sentence_transformers` BAAI/bge-m3).
**Files touched:** docker-compose image swap + init, a migration (`CREATE EXTENSION vector` + vector column + HNSW), embed-on-write path, cosine-recall query.
**Infra:** Docker image swap (verify volume mount survives), embedder endpoint config.
**GT impact:** Behavior-shift risk higher (probabilistic retrieval can deterministically miss); full re-eval + per-category metrics; rollback if not better.
**Effort:** ~2-3 days + embedder verification. **Do NOT adopt pre-emptively** — inverts YAGNI given current no-embedder state and <50 convs.

### Phase 4 (only if mandated) — mem0 library adoption
**What:** Conditional, ALL THREE must hold: (1) pgvector installed + embedder verified, (2) hand-rolled Postgres distillate store measured insufficient on a cross-conv recall eval, (3) conv volume grows past FIFO-8 + linear-scan range. Then mem0 (library mode, Apache-2.0, pgvector backend = stays Postgres-native, pluggable embedder) replaces the keyword distillate path with LLM fact-extraction + multi-signal (semantic+BM25+entity+temporal) retrieval.
**Infra:** `mem0ai` dep + its pgvector config + table.
**GT impact:** Full re-eval.
**Effort:** ~3-5 days.

## 6. CrewAI Native Memory Verdict

**KEEP `memory=False`** [customer_crew.py:204-215]. Do NOT re-enable CrewAI native memory in 1.15.5. The team's existing instinct is correct; **update the stale comment** (the "CHROMA_OPENAI_API_KEY / Memory Query-Save error spam" rationale is outdated — that API is gone in the current Unified Memory path). The real reasons now:

1. Unified Memory defaults to OpenAI `text-embedding-3-large` + an analysis LLM, neither configured in this env — lazy init raises `RuntimeError`, exactly the "Memory errors spammed" the team saw.
2. **CRITICAL scoping defect** — `Crew(memory=True)` auto-creates `root_scope=/crew/{crew_name}` (per-**CREW-NAME**, NOT per-user/session), and the auto-save/auto-recall hot paths call `remember_many`/`recall` with **NO source/private filter**, so with one shared `build_customer_crew` factory users **GUARANTEE cross-contaminate** each other's memories (user A's "allergic to peanuts" surfaces in user B's recall) — a privacy + correctness defect for a multi-user assistant.
3. The only leak-safe usage (per-request `MemoryScope(root_path=f'/user/{user_id}')`) requires threading `user_id` through the crew factory, an embedder, AND LanceDB-on-local-disk (new infra, not in the Postgres dump, docker-volume-persist concern) — a clear YAGNI violation when Postgres already holds the source of truth and the session-user-id gap must be fixed regardless.

Native memory is a poor fit for BOTH sub-problems: P1 is a windowing problem already solved better by `chat_messages` + the structured `_format_prior_context` path; P2 is a per-user durable-facts problem already covered Postgres-native by `user_profiles.context_memory` + `active_constraints_loader`. If ever revisited: run `probe_fpt_embedding.py` first, NEVER use `memory=True` (always `Crew(memory=MemoryScope('/user/{user_id}'))`), and prefer a Postgres-native `StorageBackend` over LanceDB.

## 8. GT-Gate Considerations per Phase

`routing_accuracy` baseline = **0.82**; it is a STRUCTURAL coordinator-action metric (search/clarify/explain) decided UPSTREAM of ranking/memory-injection. Standing rule: re-run ground-truth eval + metrics after ANY change; rollback if not better.

- **Phase 1 P1** (window 4→16 + char budget + tiered gate): **routing-NEUTRAL**. Memory injection happens post-routing. Expect 0.82 ± noise. Still re-run per the standing rule.
- **Phase 1 P2** (distillate "LỊCH SỬ TRƯỚC ĐÓ" block + derived cuisine/price aggregates): routing-NEUTRAL in most cases, BUT cross-conv injection **could shift CLARIFICATION behavior** — if a past distillate answers what would otherwise need a clarifying question, the coordinator may switch clarify→search. This is the one Phase-1 change that MUST be covered by the eval; rollback if <0.82.
- **Phase 1 user_id binding + list-sessions query**: routing-NEUTRAL (pure plumbing) — but it UNBLOCKS the distillate injection, so eval it TOGETHER with the distillate block, not in isolation.
- **Phase 2** (pg_trgm+unaccent fuzzy recall): recall-quality change; same clarification-shift risk as Phase-1 distillate; re-eval.
- **Phase 3** (embeddings/pgvector): higher behavior-shift risk (probabilistic retrieval can deterministically miss); full re-eval + per-category metrics; rollback if not better.
- **Phase 4** (mem0): full re-eval; LLM-extraction-on-write is itself a flakiness vector (the team already reverted a latency-OK/net-neutral LLM addition, commit `7df007f`), so measure latency AND quality.

**Rollback cost:** Phase-1 P1 = config+formatter revert; Phase-1 P2 = column-repurpose revert (no schema migration either way → cheap); Phase-3 image swap = the only one with operational rollback cost.

## 10. OPEN QUESTIONS

1. **pgvector installed?** → **ANSWERED (DB-verified): NO** on stock `postgres:18-alpine`. Image swap to `pgvector/pgvector:pg18` is the Phase-3 prerequisite; verify the mounted data volume survives the swap (check docker-compose volume mount).
2. **FE session_id stability + user_id binding**: is `session_id` stable across page reloads on the FE, and is binding `user_id` on `chat_sessions` a **FE change** (FE sends `user_id` on session create) or a **BE change** (derive from auth/cookie at `_ensure_session` [chat_message_repository.py:103-110])? Determines whether P2 needs a backfill of existing NULL `user_id` rows or just a forward-going fix.
3. **Embedder availability**: does `FPT_API_KEY` authorize an embeddings endpoint (bge-m3 / Qwen3-Embedding-8B / FPT-VN-Embedding)? `probe_fpt_embedding.py` exists but is UNRUN — this single result blocks the entire pgvector/Phase-3 and CrewAI-memory decision. Also: is the company vLLM gateway a better summarizer/embedder host than FPT?
4. **Dead column status**: is the DEAD `user_profiles.interaction_history` JSONB **reserved** (substrate for future decay, per the `interaction_events` note) or **vestigial** (safe to repurpose)? Same for `chat_sessions.context_snapshot_json` — confirmed unused in the memory path, but confirm no other subsystem reads it before repurposing as the per-conv distillate store.
5. **Real P95 conversation length** in turns? Needed to confirm the rolling summarizer is truly YAGNI vs needed at ~30 turns (Phase-1 instrumentation answers this).
6. **Is `chat_sessions.user_id` ever populated in practice today, or always None?** Determines whether P2a needs a backfill or just a forward fix.
7. **Summarization-cost governance**: who owns the per-turn vs per-session-close trigger policy for the distillate LLM call?

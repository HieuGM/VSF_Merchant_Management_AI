## Key Insights
- `confirm_delta`/`reject_delta` routes ALREADY EXIST as stubs at `POST /api/v1/users/{user_id}/profile/deltas/{delta_id}/{confirm|reject}` — implement in place (no new route prefix).
- Proposals are EPHEMERAL: `delta_id` is generated by `new_id("delta")` in `preference_service`, returned to FE, NEVER stored server-side. So `/confirm` CANNOT look up a delta by id — it must accept the delta body {field, operation, value}. `delta_id` (path) = idempotency/correlation key stored in `evidence_refs`.
- `preference_events` is append-only audit (`status`, `scope`, `source`, `evidence_refs_json`); `user_profiles` is the mutable profile. Confirm writes BOTH: event(status=confirmed, scope=confirmed_global) + applies delta to profile. Reject writes event(status=rejected) only.
- `UserProfileRepository` is read-only today → add `apply_delta(field, operation, value)` (set/add/remove semantics per `PREFERENCE_OPERATIONS`).
- FE `PreferenceSuggestion` TS interface lacks `delta_id`; `SuggestionRow` has no buttons → both must change. Backend already includes `delta_id` in `ProfileDeltaSuggestion`.

## Requirements
- F1: `POST .../deltas/{delta_id}/confirm` body `{field, operation, value, confidence?, rationale?, session_id?}` → validate operation ∈ {add,remove,set}; field ∈ whitelist; append preference_event(confirmed) + apply to user_profiles; return updated profile snapshot.
- F2: `POST .../deltas/{delta_id}/reject` → append preference_event(rejected); no profile mutation; return `{ok:true}`.
- F3: Field whitelist: `liked_cuisines, disliked_cuisines, spice_tolerance, dietary, budget_level, distance_preference_km`. Reject others with 400.
- F4: Idempotency: repeating the same `delta_id` confirm does not double-apply (check existing event by evidence_refs containing delta_id; if confirmed already, return current profile without re-applying).
- F5: Propose path unchanged — `propose_profile_delta` tool + `preference_service.propose_deltas` remain side-effect-free (verified by existing test `test_customer_context_tools_db.py`).
- F6: FE: each suggestion card gets "Lưu"/"Bỏ qua" buttons; on confirm, call client, mark card as saved (disabled state).

## Architecture
```
PreferenceEventRepository (NEW) — append-only, Session-scoped
  + append(user_id, session_id, field, operation, value, scope, source, status, evidence_refs) -> event_id
  + find_by_evidence(delta_id) -> bool   # idempotency check

UserProfileRepository (EXTEND)
  + apply_delta(field, operation, value) -> UserProfilePublic   # set/add/remove
  (get_by_id stays; repo now read+write within a single Session)

preference_confirm_service (NEW, backend/services/) — pure orchestration, owns a SessionLocal tx:
  confirm(user_id, delta_id, body) -> profile | raises
  reject(user_id, delta_id, body) -> None

routes/user_routes.py — replace not_implemented bodies
```

## Implementation Steps
1. `PreferenceEventRepository.append(...)`: build `PreferenceEvent(event_id=new_id("evt"), ..., status, scope, source="user_confirm"|"user_reject", evidence_refs_json=[delta_id])`, add, commit. `find_by_evidence(delta_id, status)`: query `evidence_refs_json` contains delta_id with given status.
2. `UserProfileRepository.apply_delta`:
   - `set`: setattr(row, field, value) (scalar fields); for list fields use replace.
   - `add`: list field → append if absent.
   - `remove`: list field → filter out.
   - Validate field whitelist; commit; return `_to_public(row)`.
   - `distance_preference_km`/`budget_level`/`spice_tolerance` = scalar; cuisines/dietary = list.
3. `preference_confirm_service.confirm(user_id, delta_id, body)`:
   - Open `SessionLocal`; begin tx.
   - If `find_by_evidence(delta_id, "confirmed")` → return current profile (idempotent).
   - `UserProfileRepository(db).apply_delta(...)` (creates row if missing — upsert).
   - `PreferenceEventRepository(db).append(..., status="confirmed", scope="confirmed_global", source="user_confirm")`.
   - Commit; return profile.
4. `preference_confirm_service.reject(...)` — append rejected event, commit.
5. Routes: parse `ConfirmDeltaRequest`; call service; return profile (confirm) / `{ok:true}` (reject). Wrap errors → 400 for validation, 404 if user absent on read.
6. FE client: add `delta_id` to `PreferenceSuggestion`; `confirmDelta(userId, deltaId, body)`, `rejectDelta(userId, deltaId)`.
7. FE `SuggestionRow`: props gain `onConfirm`/`onReject` (wired from `use-customer-chat` or local). Add buttons "Lưu"/"Bỏ qua"; on confirm set local `saved=true` → button becomes "Đã lưu" (disabled). Use the suggestion's `delta_id`.
8. py_compile backend; `tsc --noEmit` on FE; existing `test_customer_context_tools_db.py` must still pass (propose-only invariant).

- Field not in whitelist → 400.

## Risk Assessment
- **R1 Concurrent confirms race**: two simultaneous Lưu on same field — DB tx + last-write-wins on profile; both events audited. Acceptable for single-user profile.
- **R2 FE delta_id missing** (old backend responses): guard — hide buttons when `delta_id` absent.
- **R3 Profile row absent**: `apply_delta` must upsert (create `UserProfile` row) — else first-ever confirm 500s.
- **R4 Guardrail drift**: keep propose path untouched; CI test is the canary.

## Security Considerations
- `user_id` in path must match an authenticated session in prod (auth middleware out of scope here — note for hardening). For now trust path param parity with request body user_id.
- Field whitelist prevents arbitrary column writes (e.g. no touching `updated_at`/PK).
- `value` validated by type per field (list fields reject scalars) — add light validation in `apply_delta`.
